1. 第一次使用與日常啟停

一般操作以 WebAdmin 為主。先啟動 WebServer，再在瀏覽器選擇要控制的 Profile；每個 Profile 對應一組播放清單及一個 Player。

  1. 在播放電腦登入原本的 Windows 使用者，確認電視與副螢幕已連接、Windows 能辨識它們。
  2. 開啟桌面捷徑 ScreenSplitter WebServer，或執行安裝根目錄的 run_webserver.bat。
  3. 在播放電腦開啟 http://127.0.0.1:5000/；從同一內網的管理電腦操作，改用 http://播放電腦IP:5000/。這裡的 127.0.0.1 永遠指目前開瀏覽器的電腦。
  4. 選擇 default，設定螢幕與播放清單，按「儲存」。首次空白設定可依第 4、5 節建立一個場景與分區。
  5. 按播放控制器 ▶。離線時會要求啟動所選 Profile 的 Player；執行中則依目前狀態切換播放／暫停。
  6. 若有第二台螢幕，再選擇 screen2，確認其內容與目標螢幕，另按一次 ▶。最後實際查看兩台螢幕。

Web 開得起來，不代表 Player 已啟動。兩者是不同程序；網頁編輯器與看板網站也不是同一個服務。

要做的事操作與作用
啟動目前畫面WebAdmin 選 Profile → ▶。也可在播放電腦執行 Player\Player.exe --profile default，副畫面改成 --profile screen2。
關閉一個 PlayerWebAdmin 選正確 Profile →「關閉」。會先要求正常退出，再清理該 Profile 遺留的執行程序；等幾秒確認完成。
關閉所有 Player「全部關閉」作用於 WebServer 列出的全部 Profile，不會關掉 WebServer。
停止 WebServer使用安裝根目錄 kill_webserver.bat；其作用是結束本機同名 WebServer 程序樹，並非逐 Profile 控制。停止後無法使用 WebAdmin/API；必要時先關閉 Players。
關閉管理介面關閉瀏覽器分頁或桌面 Admin 視窗不等於關閉 Player；播放會繼續。
開啟本說明WebAdmin 頁首「使用說明」會另開分頁；桌面 Admin 的「使用說明」或 F1 直接開本機文件。也可使用開始選單「ScreenSplitter → 使用說明」，或雙擊 docs\usage.html。

安裝包的 run_player.bat 不帶參數時，先等待約 20 秒讓顯示器拓撲穩定，再啟動 default 與安裝根目錄下有設定檔的其他 Profile；帶 Profile 參數時只啟動指定項目。每個包裝程序只在 Player 非正常退出時等待約 5 秒重試；正常「關閉」不會被它立即拉回。

若實際資料放在 %APPDATA%，上述 BAT 不會自動枚舉那裡的其他 Profile。請用 WebAdmin 逐一啟動，或執行 run_player.bat screen2。WebServer 的自啟選項與此 BAT 是兩套不同的啟動入口。

2. 系統用途與模組

ScreenSplitter 將一台 Windows 電腦上的螢幕劃分為多個區域，播放網頁、本機影片、外部程式或 RDP 視窗，並依場景順序輪播。它負責排版、視窗與場景切換；外部網站的資料、登入、地圖服務及業務邏輯仍由各網站負責。

模組／名詞負責內容
WebServer / WebAdmin提供 TCP 5000 的網頁編輯器、設定儲存、Player 控制與診斷 API。畫面上「全域系統配置」是目前 Profile 的設定，不是一次更改所有螢幕。
Player讀取單一 Profile 設定、配置分區、輪播、處理 IPC、螢幕恢復與排程重啟。控制 Profile 另負責鬧鐘與浮動控制入口。
WebViewPlayer以 Microsoft Edge WebView2 顯示網頁與預設 HTML5 影片。一般以每 Profile 的共用 host 管理多個視窗；特定分區可選獨立程序。
AdminTool本機 Qt 桌面編輯器。可編輯基本場景、分區並控制 default，功能範圍與 WebAdmin 不完全相同。
Profile一份播放設定、一套 IPC/LOG/網站資料及一個 Player。名稱例如 default、screen2；名稱本身不會自動選中第幾台螢幕。
場景 Scene播放清單中的一頁，包含名稱、停留秒數、列／欄數與多個分區。
分區 Zone場景內一塊顯示區域，包含類型、內容、位置、尺寸及相關選項。Zone 編號從 0 開始。

執行環境需要 Windows 圖形桌面、相容的顯示驅動及 WebView2 Runtime。網頁需要的 DNS、內網路由、外部圖磚連線或帳號權限，並不會由安裝 ScreenSplitter 自動提供。WebAdmin/API 預設沒有登入驗證，應放在既有的受控內部網路；需要限制來源時，可在資料目錄建立 api_access.json（見第 15 節），不影響播放；它也不是 Windows 服務或開機前的登入替代方案。

3. Profile 與儲存生效

選擇與新增

  1. 先確認頁首 Profile 下拉選單。瀏覽器會記住上次選擇，因此重新開啟時不一定停在 default。
  2. 新增前，先切到想複製的來源 Profile，完成編輯並按「儲存」。
  3. 輸入新的 Profile 名稱後按「新增」。建議用 screen2、screen-3 等英數名稱；後端接受英數、底線、點、連字號，其他字元會被整理，最長 64 字元。
  4. 系統複製來源已存到磁碟的 config.json，並切換至新 Profile。重新指定目標螢幕、內容與重啟設定後儲存。
  5. 確認新 Profile 的目標螢幕與既有 Profile 不衝突，再啟動 Player。

複製只涵蓋設定，不會複製網站登入資料、快取、影片或外部 EXE。若名稱已存在，建立動作不會覆蓋其既有 config。現有 WebAdmin 沒有 Profile 刪除／重新命名按鈕；交接時保留清楚命名與資料位置，移除需求交由維護者在停播、備份後處理。

什麼時候會生效

一般編輯先留在瀏覽器，按「儲存」才寫入所選 Profile，成功後 WebAdmin 另送出 RELOAD，Player 重讀設定與目前場景。Player 未啟動時，設定仍可儲存，等下一次啟動載入。Player 也監看設定檔變化。

切換 Profile 或重新整理前先儲存。切換會重新讀取另一份設定，未儲存的畫面編輯不會自動保留；不要同時由兩個舊分頁或桌面 Admin 編輯同一 Profile。儲存提交整份設定，後存者可能覆蓋前存者的內容。

「偵測 → 選擇螢幕」是例外：選擇後會立即調整畫布、縮放既有分區並自動儲存。新版對省略 screen_device 的舊設定提交會保留磁碟上原綁定，但這不是整份設定的多人合併機制。

操作作用域
儲存、上一頁、下一頁、雙擊跳場景、播放／暫停、關閉WebAdmin 目前選擇的 Profile。
全部關閉WebServer 列出的所有 Profile。
鬧鐘、浮動控制球控制 Profile default。screen2 等次要 Profile 不執行鬧鐘。
開啟手冊、關閉管理分頁不會寫入設定，也不會改變目前播放。

4. 場景、排序與播放控制

  1. 按左側「新增 ADD」，輸入有意義的名稱，例如「生產進度」或「安全事件」。新場景預設 10 秒、2 × 2，仍需用「自動排列」建立分區。
  2. 設定時長與列／欄，建立分區內容；按「儲存」。
  3. 拖曳左側場景調整順序，儲存後依清單由上而下輪播，最後一頁回第一頁。
  4. 單擊場景是選取編輯；雙擊是要求 Player 立即跳到該索引。新增或排序後先儲存，再雙擊，避免編輯器與 Player 的索引不同。
  5. 刪除場景會要求確認；儲存後才寫入設定。空清單不會產生可播放內容。
設定／按鈕實際行為
時長大於 0到期切到下一場景。這是場景停留時間，不會等待影片自然播放完畢。
時長 = 0固定停在該場景，WebAdmin 顯示「固定」。仍可手動上一頁、下一頁或跳轉。
暫停停止自動換場景；頁面中的資料更新、影片或外部程式不一定停止。不是整台播放器或所有媒體的暫停鍵。
繼續播放依目前場景完整時長重新計時；不是接續原本剩餘秒數。0 秒場景仍維持固定。
暫停中手動換頁／重載保留暫停狀態，顯示新的場景，但不重新啟動自動輪播。

建議先把每一頁單獨顯示到確認內容穩定，再開始整輪驗收。場景切換會涉及網頁建立、影片載入或外部視窗調整，短秒數不代表內容一定來得及完成載入。

在 Player 畫面現場操作

default 畫面有「☰」浮動控制入口，點一下顯示／收起控制列，可按上一頁、暫停／播放、下一頁或「關閉播放」。Player 收到 Esc 或自身可接收的長按事件時，也可切換控制列；外部網頁／EXE 可能先接收鍵鼠事件，因此遠端維護以 WebAdmin 控制最直接。screen2 預設不建立浮動控制球。

5. 分區與版面編輯

建立與調整版面

  1. 確認全域畫布寬高與目前螢幕用途。列／欄各可設定 1–10。
  2. 按「自動排列 AUTO」，以列 × 欄產生等分分區，並重新排好前面這些分區的 x、y、w、h。
  3. 在預覽內拖曳分區移動位置；拖右下角縮放控制點調整寬高。也可直接輸入「座標 POS」與「尺寸 SIZE」，用數值做精確調整。
  4. 「同步尺寸 SYNC」把 Zone 0 的寬、高套給其他現有分區；它不替其他分區重新排列位置。
  5. 用分區卡片的 × 刪除區域；選中預覽分區時可用 Delete，輸入欄位內的 Delete 仍是文字編輯。最後儲存。

x、y 是相對此 Profile 畫布左上角的位置；w、h 是畫布單位下的寬高。這些不是 Windows 全桌面的螢幕座標。預覽是配置示意，不是實際網頁、影片或 EXE 的即時畫面。

列／欄與分區數量須一致。Player 最多使用前 rows × cols 個分區。WebAdmin 減少列／欄不一定刪除陣列末端的舊分區；「自動排列」也不會自動刪除多餘項目。若看得到卡片卻沒有播放，先查編號是否超出這個上限。

重疊分區會在預覽提示碰撞；直接輸入仍可形成重疊。避免把重要內容放在畫布外，維持正的寬高。再按「自動排列」會覆寫已有的手動位置與尺寸，應先完成需要保留的設定備份。

全域畫布尺寸變更

更改寬高後儲存，或從偵測清單選螢幕，WebAdmin 會按舊／新畫布比例縮放全部場景既有的分區位置與尺寸。Player 再將畫布映射到當下 Qt 邏輯螢幕與外部視窗實體座標。變更解析度後要檢查所有場景，不只目前預覽的一頁。

6. 網頁、影片、EXE 與 RDP

類型內容欄位播放方式與限制
網頁 WEB完整網址，例如 http://內部主機:連接埠/看板。預設以 WebView2 顯示。網站須在播放電腦可連線；管理電腦開得到不等於 Player 開得到。需要登入的網站，使用的是 Player 自己的網站資料環境。
影片 VIDEO播放電腦可讀的檔案完整路徑，例如 D:\Media\demo.mp4。預設生成本機 HTML5 影片頁交由 WebView2 播放，循環、自動播放、靜音；畫面採 cover 填滿，長寬比不同可能裁切。實際格式須由 WebView2/系統支援。既有進階設定也可使用 VLC 後端。
程式 EXE可執行檔路徑；必要參數須正確引號，例如 "D:\Display App\Viewer.exe"。Player 啟動／尋找外部視窗，再定位、縮放與管理顯示。不是把任意程式轉成網頁；程式自己的最小尺寸、登入框、權限、特殊渲染或多視窗可能影響結果。
遠端 RDP遠端電腦 IP 或主機名稱。呼叫 Windows mstsc /v:目標，仍需原有 RDP 權限、憑證確認與登入。現有追蹤以 mstsc 視窗為主，不保證多個同時 RDP 工作階段能各自正確綁入不同分區。

內容欄位指定的是播放電腦的路徑，不是目前用來開 WebAdmin 的電腦。WebAdmin 沒有影片／EXE 上傳功能；先將檔案部署到播放電腦，並確認執行 Player 的 Windows 帳號能讀取。網路分享路徑還依賴連線與該帳號的存取權限；登入後才連上的磁碟機不保證能在自動啟動當下使用。

分區選項的適用範圍

  • 強制更新／cache_bust：只針對網頁，每次進入場景以新的查詢參數導覽，詳見下一節。
  • 獨立程序／isolate_webview：供 WebView2 內容隔離使用；一般網頁先維持預設，共用環境有特定問題時才在該區域啟用。它不會把 EXE 或 RDP 改成 WebView。
  • 縮放 ZOOM／scale：WebAdmin 有此欄位，但目前預設外部 WebView2 命令未套用這個值；只有舊的內部 QtWebEngine 路徑使用 setZoomFactor。不要把它當作預設 WebView2 的可靠文字縮放功能；優先調整網站本身支援的顯示設定與分區尺寸。
  • 強制去邊框／strip_border：桌面 Admin 可設定，Player 對外部視窗依此處理，預設為 true。不同 EXE 不一定接受；仍需逐一驗收。

既有 global_settings.video_backend="vlc" 會改用 VLC，程式優先尋找隨包的 Player\VLC\vlc.exe，再查其他既有位置；這是設定檔層級選項，WebAdmin 沒有後端切換按鈕。維持現場已驗收的選擇，別只因資料夾中有 VLC 就認定所有影片都由它播放。

7. WebView、強制更新與登入狀態

共用與獨立模式

「共用」是同一個 Profile 裡的 WebView host；default 與 screen2 的 host、命令、狀態及網站資料各自分開。一般模式會在場景交接後關閉不再需要的網頁視窗，預設不讓全部看板永久躲在背景執行。

項目一般共用 host獨立 WebView
執行方式每 Profile 一個 host 管理分區視窗。分區另啟 WebViewPlayer；離開場景後關閉，回來重新啟動。
網站資料位置<Profile資料夾>\web_profile\ExternalHost<Profile資料夾>\web_profile\External\<WebView tag>
適用情況一般看板預設方式。特定網站的媒體、渲染或共用環境出現可重現問題時，單區域隔離驗證。
診斷host 狀態可出現在 webview_status.json 與 diagnostics API。主要查看自己的 webview_<tag>.log；不保證出現在共用 host 的 windows／last_probe 清單。

獨立模式同時改變程序與網站儲存資料夾，可能需要重新登入，也可能讓網站看到另一套 localStorage 設定。它不是「清除原本資料」；切換模式後正常，只能先縮小問題範圍，不能直接認定原環境只有 HTTP 快取問題。

強制更新不是清除全部快取

啟用網頁「強制更新」後，Player 在每次進入場景時加入／替換 _screensplitter 查詢參數，保留其他查詢參數與片段。單次場景內的視窗定位迴圈會沿用同一 token，不是每半秒刷新網站。

  • 頁面重新導覽、圖磚／圖片的 HTTP 快取、Cookie、localStorage 是不同層次。
  • 強制更新不會刪除 Cookie、登入憑證、網站設定或本機用量計數；也不保證網站的 Service Worker 或所有子資源都忽略快取。
  • 普通 Edge/Chrome 與 Player 的 WebView2 使用不同資料環境；一邊已登入，不代表另一邊已登入。
  • 獨立 tag 包含 Profile、場景索引與分區索引。重新排序場景／分區可能改變對應資料目錄，交接時不要只靠「第幾頁」記錄登入狀態。

有問題時先保留 LOG 與資料位置。直接刪除 web_profile 會影響登入與網站設定，並不能用來證明原因；還原或清理前先依備份程序處理。

8. 螢幕指定、DPI 與喚醒

  1. 先在 Windows 顯示設定確認延伸桌面、實際排列、解析度與縮放比例；要分別播放不同 Profile，應能辨識到不同螢幕。
  2. WebAdmin 選 default → 全域系統配置「偵測」。列出的螢幕來自WebServer 所在電腦，不是管理電腦。
  3. 選擇 default 應使用的螢幕。此動作會保存設備識別 screen_device、位置與畫布尺寸，並立即儲存。
  4. 切到 screen2，選它應使用的另一台螢幕，再實際查看兩個 Player。
  5. 記錄螢幕名稱／device ID、解析度、Windows 縮放百分比、排列與連接埠，作為搬機及喚醒測試基準。

有明確設備識別時，Player 優先用識別找螢幕；舊設定只有座標時仍有座標判斷。螢幕掉線會使座標／主螢幕排列改變，因此不要只靠「0,0」或「螢幕 1」推定目標。

4.3.7 起的缺席等待／返回行為

已指定的目標螢幕不存在時，Player 隱藏此 Profile 的畫面及追蹤視窗，停止場景計時，等待目標回來；IPC、退出控制及控制 Profile 的鬧鐘仍可運作。螢幕回來後恢復目標位置並重建原場景，保留使用者的暫停選擇及 0 秒固定設定。等待期間不應把該 Profile 的畫面轉放到另一台螢幕。

Windows、連接線、轉接器或顯示驅動不一定會在螢幕關電時回報移除；若作業系統仍把它視為在線，程式也無法僅靠這些事件知道實際面板是否亮起。喚醒必須在現場依實際硬體驗收。

解析度與 DPI 的判讀

設定畫布、Qt 邏輯尺寸、Win32/WebView 實體視窗尺寸可能不同，例如 150% 縮放下不能直接拿兩組數字相比就判定顯示錯誤。先比較螢幕 device、Windows 排列、DPR 與實際顯示；不要一遇到尺寸不同就改掉既有縮放比例。

換螢幕、換顯示卡／連接埠或搬機後，原識別可能改變。此時先用「偵測」確認新設備並重新選擇，不要刪除整份設定。若畫面仍跑錯位置，查看 LOG 的 [Screen Wait]、[Screen Return]、[Screen Restore] 與 [Layout]。

9. 鬧鐘、排程重啟與自動啟動

設定使用方式與邊界
中餐／起床／下班鬧鐘只在 default 開啟相應開關並設定時間，儲存後由 default Player 執行。screen2 的控制欄位停用，後端也會把次要 Profile 的鬧鐘開關存為 false。
重啟 Restart每 Profile 的 Player 重啟間隔，單位分鐘，範圍 0–1440；0 關閉。不是 Windows 重開機，也不是每天固定時刻的排程。缺少設定時程式預設 60 分鐘。
Web 自啟 Auto已打包 WebServer 啟動時，檢查各 Profile 的此選項，對已啟用且離線者啟動 Player。預設 false；不是持續監控 Player 的常駐重啟服務。原始碼開發模式不執行這段啟動自檢。
Windows 登入自啟安裝程式在目前使用者 Startup 建立「ScreenSplitter Players」捷徑，執行 run_player.bat。這與 Web 自啟選項不同；不是系統尚未登入時啟動。

排程重啟會先建立同 Profile 的接替 Player，等待舊 PID 正常退出再啟動。若接替程序建立失敗，舊 Player 保持運作；成功後是重新啟動程序，不應假定會保留上一程序的倒數或暫停狀態。更改間隔會重新計算該定時器。

鬧鐘實際條件

鬧鐘依播放電腦本機時間檢查，default Player 必須正在執行。音檔名稱為 lunch.mp3、wakeup.mp3、offwork.mp3；優先查 Player 的 music 資料夾，再查資料目錄及上一層既有 music。可用音檔不存在／音訊模組不可用時，會嘗試 Windows 系統提示音。

程式在目標時間後 70 秒內允許觸發，不會為離線很久的鬧鐘整天補播。同一次程序執行中每日每類只記一次；去重記憶在程序內，重啟落在容錯區間仍須注意可能再響。鬧鐘不會替電腦從睡眠喚醒，也不保證螢幕喇叭或 Windows 音量已開啟。

前場景清理與 WebView2 host 是目前 Player 固定的執行策略；WebAdmin 已移除其切換控制。不要照舊版說明尋找「關閉 host」或直接以舊進階鍵覆蓋目前行為。

10. 桌面 Admin 使用與限制

以桌面「ScreenSplitter Admin」或 run_admin.bat 開啟。左側可新增／刪除場景、拖曳排序與儲存；右側可設定名稱、秒數、列／欄，拖拉預覽區域，編輯類型、內容、x/y/w/h、去邊框及獨立 WebView。雙擊場景可送出跳轉，控制列提供播放與換頁。

改完先按「儲存設定」；Player 透過設定檔監看讀入。關閉 Admin 視窗不會自動關閉 Player。本版的「使用說明」與 F1 直接用預設瀏覽器開啟離線手冊，不需要先啟動 WebServer。

項目桌面 Admin 現況操作建議
多 Profile沒有 Profile 選單；控制用 IPC 路徑直接取資料根目錄。只用於 default。screen2 請用 WebAdmin；不要以環境變數當作完整多 Profile 控制支援。
0 秒固定場景時長輸入下限為 1；載入 0 後再儲存可能被改成 1。含 0 秒場景的設定用 WebAdmin 維護。
螢幕偵測以面積最大的螢幕取得實體解析度，縮放分區並儲存；不是 WebAdmin 的設備選擇器。雙螢幕綁定請用 WebAdmin「偵測 → 選螢幕」。
列／欄減少會按列 × 欄截短分區清單。縮小前備份，避免丟失末端內容。
進階設定沒有 WebAdmin 的強制更新、鬧鐘、排程重啟、Web 自啟 UI；也沒有一般 WebView2 網頁縮放功能。相關設定以 WebAdmin 或由維護者核對設定檔。
在線狀態約 3 秒沒有新狀態即顯示離線，與 Web API 的閾值不同。短暫顯示離線先比對實際畫面、時間戳與程序，不要立即重複啟動。

11. 實際資料位置與檔案

先查正在使用的 DATA_DIR，不能把路徑寫死。config_manager.py 將 Player、WebServer、AdminTool 的父資料夾視為共同根目錄 SHARED_ROOT；原始碼執行時通常就是原始碼所在目錄。

  1. 若 SHARED_ROOT 可寫，DATA_DIR 就是 SHARED_ROOT，即設定與程式並列的可攜式模式。
  2. 若不可寫，改用執行該程序之 Windows 使用者的 %APPDATA%\ScreenSplitter。
  3. default 資料在 <DATA_DIR>；其他 Profile 在 <DATA_DIR>\profiles\<Profile名稱>。

安裝腳本可能建立 C:\ScreenSplitter_Data，但目前程式沒有以此資料夾作為固定設定來源。只看到此資料夾，不能認定備份了它就完成備份。原始碼中的舊註解也不能取代實際路徑判別。

如何確認

唯讀查看 /api/profiles 的 data_dir／config_path，或 /api/logs?profile=default 的 data_dir；Player 的啟動／除錯紀錄也會記錄 Profile、Data Dir 與 IPC Paths。WebServer、Player、AdminTool 應使用同一安裝與相同 Windows 使用者權限；一個以其他帳號或不同權限啟動，可能讀寫到另一個資料根。

檔案／資料夾用途與備份需求
config.json該 Profile 的畫布、螢幕綁定、鬧鐘／重啟與播放清單。必要備份。
profiles\…\config.json其他 Profile 設定。備份不能只拿根目錄那一份。
web_profile網站設定、Cookie、儲存與快取所在樹。需要保留網站狀態時，在停止 Player 後備份；跨電腦／Windows 帳號不保證登入可移植。
ipc_cmd.txt、ipc_status.json執行中的指令與心跳。不是人工還原播放狀態的設定來源；搬機不要以舊副本取代新狀態。
api_access.json選用的 WebAdmin/API 存取限制（權杖與允許 IP，見第 15 節）。不存在即為開放模式；內含權杖，備份時視同密碼保管。
webview_cmd.json、webview_status.json該 Profile 的 WebView host 命令與診斷狀態。屬執行期資料。
*.log、stdout.txt、stderr.txt故障證據；重啟前先保留。不是所有紀錄都會永久累積。
影片、EXE、客製 music多半位於 config 指向的外部位置或 Player\music。設定備份不會自動收集這些檔案。

Profile 新增只複製 config；刪除安裝資料夾、切換 Windows 使用者或改變目錄可寫性，都可能改變之後讀取的資料。遇到「設定像消失」時，先查新舊 DATA_DIR，再談重建。

12. 安裝、升級與卸載

安裝／升級順序

  1. 記錄目前版本、安裝位置、Windows 執行帳號、實際 DATA_DIR 及 Profile 清單；依下一節備份。需要保留事故證據時先匯出 LOG。
  2. 在 WebAdmin「全部關閉」Players，確認內容視窗與對應程序結束，再關閉 Admin、停止 WebServer。
  3. 使用已確認版本的 ScreenSplitter_Setup_4.3.8.exe，或交付時同內容的 ScreenSplitter_Setup.exe，安裝到原有安裝位置。不要只覆蓋一個 Player.exe 而混用其他版本的 _internal 與 WebViewPlayer。
  4. 安裝包部署程式、資源、啟動 BAT 與 docs\usage.html；不把開發電腦的現場 config、profiles 或網站資料當成預設內容發送。
  5. 啟動 WebServer；核對原 Profile、螢幕綁定與內容仍在，再啟動 Players。依第 18 節實際驗收兩台螢幕與每種內容。

安裝程式採目前使用者權限，實際目錄以安裝精靈及捷徑為準，可能位於使用者的 LocalAppData\Programs；不要假定每台都在 Program Files 或與另一台使用者路徑相同。若安裝後由精靈啟動 WebServer，只有啟用 Web 自啟的 Profile 會被該入口自動啟動。

資料保留與卸載邊界

正常原位置升級不應覆蓋使用者 config 或網站資料。安裝清理僅針對 4.3.5 曾誤帶的特定 ICU DLL；不是清空設定。仍需先備份，因為選錯安裝位置、執行帳號改變或手動刪資料夾會造成另一種結果。

卸載會移除安裝程式登記的程式檔與捷徑；使用期間產生的設定／LOG／網站資料，以及位於 %APPDATA% 的資料不應被視為一定已刪除或一定會保留。卸載不是備份，也不是網站帳號登出的替代方式。卸載後如要移除殘留資料，先確認實際 DATA_DIR 與備份，交由維護者針對明確路徑處理。

4.3.5 的 Qt DLL 匯入問題

歷史案例為 ImportError: DLL load failed while importing QtWidgets: 找不到指定的程序。當時打包環境把其他工具的 ICU DLL 帶進 Qt 程式，遮蔽 Windows 所需版本。4.3.6 起採乾淨建置 PATH、拒收意外 ICU 並執行真實 Player 啟動驗證，後續版本包含此修正。

可從 4.3.5 加既有臨時修補直接升級完整 4.3.8，不必先裝中間版本。若仍出現相同錯誤，先保存完整訊息與實際執行路徑，檢查是否啟動舊副本／混用資料夾。不要任意從網路下載同名 DLL 塞入 _internal。

13. 備份、還原與搬機

備份

  1. 從 API／LOG 確認 DATA_DIR、每個 Profile 與安裝位置；記下版本及備份時間。
  2. 先保存要查的 LOG，再正常關閉 Players、Admin 與 WebServer，使設定及網站資料不再持續寫入。
  3. 複製根 config.json、完整 profiles 設定樹，以及需要保留的 web_profile、客製 music。若 DATA_DIR 就是安裝根，可整個保留一份版本化備份，但要清楚區分程式與現場資料。
  4. 另外收集 config 所指向的影片、外部 EXE 及其必要資源。記錄網站負責人、登入移交方式與外部路徑，不把密碼或 API key 寫進公開手冊。
  5. 檢查備份真的有每個 Profile 的 config、可讀且日期正確；把副本放在不會隨此次安裝／清理刪除的位置。

還原／搬機

  1. 新機先安裝完整程式與必要執行環境，以預定 Windows 帳號啟動一次 WebServer，確認新機實際 DATA_DIR，再停止它。
  2. 保留新機現狀備份後，把設定放回對應資料根與 profiles 子目錄；不要把舊 ipc_cmd、ipc_status 或 webview_status 當設定還原。
  3. 部署影片／EXE 等外部檔案。路徑不同時更新內容欄位；網路分享與 RDP 權限在新帳號下重新驗證。
  4. 如需網站資料，僅在程序都停止時還原其資料樹；Cookie 可能與原 Windows 帳號／電腦綁定，因此仍準備合法重新登入。不要保證複製 web_profile 就能移轉登入。
  5. 開 WebAdmin，逐 Profile 重新偵測並選擇新機螢幕。檢查 DPI、音訊輸出、自啟、重啟間隔與每個場景。
  6. 先驗收新機，再停用舊機，避免兩邊同時播放／產生鬧鐘或外部網站額外負載。保留能回退的原機資料與安裝版本。

14. 故障排除

先記錄發生時間、Profile、場景／Zone、實際看到的症狀、最近變更，並保存當次 LOG。先分清「管理服務沒開」「Player 沒啟動」「視窗位置錯」「網頁內容局部失敗」，再選處理方法。

症狀先查什麼／怎麼處理
WebAdmin 打不開在播放電腦測 127.0.0.1:5000，確認 WebServer 程序與 web_server.log；本機通而遠端不通再查 IP、路由、防火牆、5000 是否被其他程式占用。不要把外部看板網站的故障當成 WebAdmin 故障。
Web 能開，Player 不見選對 Profile，確認已按 ▶；Web 自啟可能關閉。查指定螢幕是否缺席、stderr/startup_crash/restart.log，以及 Player.exe 是否來自正確安裝目錄。
顯示離線但螢幕還在動比對 status_age、實際場景變化與 WebView 狀態。心跳寫入或主執行緒可能延遲；不要僅憑一次離線就判斷程序已死或反覆啟動。
輪播停在一頁先查 duration 是否 0、paused 是否 true，以及目標螢幕是否進入等待。若都不是，再比對目前 scene_idx 的時間序列、例外與外部程式是否卡住。
程式到錯螢幕／開屏沒回來查 Windows 是否重新辨識到目標、screen_device 是否仍吻合、是否只有舊座標。選正確 Profile 重新「偵測 → 選螢幕」，並查 Screen Wait/Return/Restore LOG。保留其他 Profile 的設定。
網路路徑錯誤確認真正報錯的是啟動 BAT、外部 EXE、影片分享路徑或網站；用同一 Windows 帳號確認路徑與開機連線時序。舊版排程重啟曾有命令引號問題，新版已改用直接程序參數；不要先假定是交換器丟包。
網站空白／舊內容／登入失效比對該網址在播放電腦與 Player 的結果、Loaded/last_error、模式及網站資料目錄。先確認網路和登入；部署後舊頁可針對該網頁評估強制更新，不能用來替代登入或修復網站程式。
地圖灰底但標記還在網站框架可正常而圖磚失敗；可能涉及連線、服務拒絕、本機用量／時段設定或尺寸同步。共用模式且符合特定 overview 網址才有 mapDiagnostics；獨立模式需看獨立 LOG 與現場，不要清除全部儲存來猜原因。
影片黑畫面／無聲查檔案是否存在、Player 帳號是否能讀、格式是否可由目前後端播放。預設 HTML5 影片是靜音循環；無聲不等於故障。VLC 模式另查 VLC 路徑與其程序。
EXE 視窗不進分區先獨立確認 EXE 在同一使用者工作階段可啟動，再查路徑、引號、權限、最小尺寸、多視窗或特殊渲染。RDP 的登入／憑證提示仍需正常處理。
改完設定沒生效／隔天又回舊值核對選取 Profile、儲存成功、實際 config_path；關掉過期編輯分頁後重開。確認是否另一 Admin／分頁後來提交整份舊設定，或啟動了另一安裝副本。
鬧鐘沒響／重複響查 default Player 是否運作、開關與本機時鐘、音檔／喇叭／音量；核對是否於時間後容錯區間重啟，或有另一台播放電腦同時執行。

2026-09-29 的 209 案例：歷史參考

當時的 172.20.11.209 回報使用 4.3.5 加 Qt 臨時修補。LOG 顯示主 Profile 曾依舊座標認到副螢幕；當天設定已明確綁定 default → BenQ TV、screen2 → VA3456-WQHD。overview 改為獨立 WebView 後，使用者回報地圖恢復。

獨立模式同時改變程序與網站儲存目錄，所以當時未證實究竟是圖磚 HTTP 快取、localStorage 的本機用量設定，還是共用渲染狀態。另有普通瀏覽器尺寸改變後 Leaflet 局部空白的重現證據，屬網站容器尺寸更新問題；ScreenSplitter 更新不等於已修好該外部網站。

4.3.7 的螢幕等待／返回、host 延遲命令取消及診斷修正已納入後續版本。以上是歷史調查，不代表 2026-11-02 已重新驗證 209 的部署版本、即時 LOG 或硬體喚醒狀態；現況仍須現場回讀及驗收。

15. LOG 與唯讀 API

先看哪個 LOG

名稱用途
player_debug.logPlayer 啟動、Profile／路徑、排程重啟、螢幕等待／返回等重要事件；超過門檻會換成 .1 備份。
stdout.txt／stderr.txt當次 Player 執行輸出與例外。正常取得單一實例鎖後重新啟動會重寫這兩檔，先留存再重啟。

restart.log排程重啟的接替啟動資訊。確認時間、Profile、PID 是否接續。
webview_host.log共用 host 開窗、導覽、顯示／隱藏、載入與恢復事件。
webview_<tag>.log獨立 WebView 的視窗、載入與探測紀錄；tag 通常包含 Profile、場景及分區索引。
web_server.log打包 WebServer 的啟動／請求相關輸出；WebServer 每次啟動會重寫。
command_audit.logWeb 控制命令、作用 Profile、退出清理與請求來源線索；啟用存取限制後，被拒絕的請求（[AUTH] denied）也記在這裡。
window_log.txt視窗大小或狀態異常的自我修復紀錄。

API 查不到某檔不代表磁碟不存在。LOG 列表只收指定副檔名、跳過部分敏感名稱；.1 等輪替檔未必列出。搜尋也只查尾端範圍，不是全檔歷史檢索。Profile 的 LOG 查找會回退到共同根等位置，要核對回傳 path，不能把 screen2 查到的共用 restart.log 當成 screen2 自己的事件。

唯讀檢查範例

下列是 GET 讀取，使用時把主機換成實際播放電腦。內容可能含內部網址、路徑與程序資訊，交接時只保留所需且已遮蔽的片段。

http://127.0.0.1:5000/api/profiles
http://127.0.0.1:5000/api/screens
http://127.0.0.1:5000/api/status?scope=all
http://127.0.0.1:5000/api/diagnostics?scope=all
http://127.0.0.1:5000/api/logs?profile=default
http://127.0.0.1:5000/api/logs/player_debug.log?profile=default&lines=400
http://127.0.0.1:5000/api/log-search?profile=default&file=player_debug.log&q=Screen%20Return
http://127.0.0.1:5000/api/processes?scope=all

在播放電腦 PowerShell 也可只讀取得狀態：

$base = 'http://127.0.0.1:5000'
Invoke-RestMethod "$base/api/status?scope=all"
Invoke-RestMethod "$base/api/profiles"
Invoke-RestMethod "$base/api/diagnostics?scope=all"

完整設定的 GET /api/config 會呼叫 ensure_profile；對不存在的 Profile 可能建立其資料。因此純診斷先用上述狀態、Profile 及 LOG 入口，避免拿未知名稱反覆查設定。POST /api/cmd、/api/run_player、/api/config、/api/profiles 都是有操作效果的介面，不屬於這組唯讀範例。

限制遠端存取（選用，4.3.8 起）

預設 WebAdmin/API 不驗證來源，與舊版相同。需要限制時，在實際 DATA_DIR（與 default 的 config.json 同一層，可由 /api/profiles 的 data_dir 確認）建立 api_access.json；不需重新啟動 WebServer，也不影響 Player 與播放：

{
  "token": "自行產生一段夠長的隨機字串",
  "allowed_ips": ["172.20.10.5"]
}

規則：來自播放電腦本機（127.0.0.1／::1）的請求永遠允許；allowed_ips 內的 IP 不需權杖；其他來源必須附權杖。兩個欄位可只填其一。檔案存在但無法解析時只接受本機，直到修正為止。被拒絕的請求回 401，並記入 command_audit.log（每個來源每分鐘最多一筆）。原始碼模式也可改用環境變數 SCREENSPLITTER_API_TOKEN 指定權杖。

遠端讀取 LOG 或送指令時，把權杖放在 HTTP 標頭：

$headers = @{ 'X-Api-Token' = '你的權杖' }
Invoke-RestMethod "http://播放電腦IP:5000/api/status?scope=all" -Headers $headers
curl -H "Authorization: Bearer 你的權杖" "http://播放電腦IP:5000/api/logs?profile=default"

瀏覽器開啟 WebAdmin 時會先出現輸入權杖的頁面；輸入一次後以 HttpOnly Cookie 保留 30 天，權杖不會出現在網址列。移除限制只要刪除 api_access.json。/help 手冊入口維持公開。此機制只看 TCP 來源 IP，不信任 X-Forwarded-For；它不是帳號系統，權杖應視同密碼管理，不要寫進手冊或交接紀錄。

健康指標怎麼解讀

欄位可得知不能據此保證
timestamp / status_agePlayer 心跳的新舊；API 超過 8 秒標 stale/offline，桌面 Admin 閾值較短。一次逾時不等於程序已終止；時間新也不保證所有內容正確。
scene_idx / paused / total / remaining目前場景索引、暫停、總時長與計時。total=0 為固定。remaining=0 可能是暫停／固定／等待；不能只看它推定故障。
webview.windows…state / last_error / last_probe共用 host 是否載入、DOM 可讀與最近探測結果。DOM complete 不能證明圖磚、API 資料、登入或整個看板內容正常。
render_health抽樣內容是否接近整片黑／白及恢復動作線索。有非黑白像素不代表內容正確；純色頁面也可能是合法內容。
processes程序路徑、PID、命令列等輔助線索。單靠快照歸類不能判定重複 Player；須比對完整 --profile 與實際程序樹。

特定 overview 地圖診斷

共用 host 的 probe 僅在 http://itom.lkeng.com.tw:8080/overview（允許尾端斜線）加入 last_probe.mapDiagnostics。它以唯讀方式回傳地圖尺寸、圖磚 img 的 images/loaded/failed、純色 div 的 placeholders，以及網站本機保護的非機密欄位；不讀出 API key、不寫網站儲存，也不因灰圖自動重載。

  • placeholders > 0 且 carto.reason=budget：支持該 WebView 本機安全上限阻擋圖磚的判斷。
  • carto.reason=schedule／disabled：反映讀取到的本機時段／啟用設定。
  • images > 0、failed > 0：有圖磚影像載入失敗，續查連線、DNS、服務回應、快取或憑證等。
  • currentAllowed=true：只表示依已知網站本機保護條件推算可請求，不代表 API key 有效、服務端授權成功或圖磚已載入。
  • storage_unavailable／usage_unavailable：資料讀取或計數無法可靠判斷，null 不是 0。

此診斷以當時確認的網站保護規則（100,000 次本機估算上限）為依據，並非 CARTO 官方帳務統計。網站日後更版時需重新核對。overview 如果使用獨立 WebView，不會因此自動出現在共用 host 的 mapDiagnostics。也不能在管理電腦開網站管理頁，便宣稱讀到了播放電腦 WebView 的 localStorage。

IPC 與更新流程

WebAdmin 儲存經 WebServer → config_manager 寫入該 Profile config；命令則由 WebServer 寫該 Profile 的 ipc_cmd.txt。Player 定期讀取並刪除命令檔，寫出 ipc_status.json。命令檔是單一槽位，不是可靠累積佇列；不要高速連送並假定每一筆都必定依序處理。

指令作用
NEXT／PREV切換下一／上一場景。
JUMP n跳至從 0 開始的場景索引 n。
PAUSE／RESUME停止場景計時／以當前場景時長重新計時。
RELOAD重讀該 Profile 設定與場景。
EXITPlayer 正常退出。WebServer 的 EXIT API 另有依 Profile 的延後清理。

WebView host 用同 Profile 的 webview_cmd.json 批次交換 upsert/open/show/hide/close/reload/probe/exit 等命令，視窗以 tag 區分。hide/close 會取消同 tag 舊的延遲開窗命令。webview_status.json 是 host 狀態，與 Player 的 ipc_status 不同。不要讓不同 Profile 共用這些檔案或網站資料路徑。

Player 每 Profile 有單一實例 mutex；同一 Profile 重複啟動會退出新增實例。Profile 名稱整理後仍應保持簡單且彼此明顯不同，避免僅靠符號差異命名。HTTP 命令回覆成功表示請求已接受／寫入，驗收仍應查看後續狀態與實際畫面。

17. 測試與安裝包製作

本專案目前位於 D:\ScreenSplitter。2026-11-02 查核的建置 Python 為 venv\Scripts\python.exe，Python 3.11.9、PySide6 6.10.1、PyInstaller 6.18.0。專案另有 .venv 等資料夾，不能因名稱相近就混用；更換環境前先保存與核對套件版本。

回歸檢查

Set-Location -LiteralPath 'D:\ScreenSplitter'
& '.\venv\Scripts\python.exe' -m unittest discover -s tests -v
& '.\venv\Scripts\python.exe' -m py_compile player.py webview_player.py web_server.py admin.py config_manager.py build_release.py

地圖 probe 測試透過現有 Node 執行真實 JavaScript；若找不到 Node，測試會標示 skipped，不能把整體沒有失敗當成已跑過該情境。確認測試輸出的執行數、略過項目與失敗內容。UI／螢幕／影片實機驗收不由這些單元測試取代。

建立完整發行目錄與安裝檔

Set-Location -LiteralPath 'D:\ScreenSplitter'
& '.\venv\Scripts\python.exe' '.\build_release.py'
& 'C:\Program Files (x86)\Inno Setup 6\ISCC.exe' '.\setup_script.iss'

Inno Setup 路徑依實際安裝調整。build_release 會先清理專案的生成用 build 目錄，再建立 AdminTool、Player、WebServer、WebViewPlayer 四個 onedir 元件，整合成 build\ScreenSplitter_Dist；需要保留的前一版產物先另存。安裝檔輸出為 build\ScreenSplitter_Setup.exe。

建置腳本會限制 PATH，只保留建置 Python 與 Windows 必要位置，避免其他工具提供同名 Qt 依賴。整合時若 Player/AdminTool 意外帶入 _internal\icuuc.dll，建置會失敗；不可刪掉檢查、再宣稱打包成功。

腳本也會對真正要交付的 Player.exe 執行 offscreen QWidget 啟動檢查，輸出載入的 Qt／ICU 資訊。這證明封裝程式能載入 Qt，不代表所有外部網站、螢幕喚醒與現場帳號已驗收。

發版核對

  1. 確認 setup_script.iss 版本、手冊版本及交付檔名一致；確認 docs/usage.html 真的進入發行目錄與安裝包。
  2. 確認 build log 沒有元件缺漏；templates/static、WebViewPlayer 與需要的影片／音訊後端資源齊全。
  3. 確認不把現場 config、profiles、web_profile、憑證、LOG dump 或測試資料夾打包給另一台電腦。
  4. 用實際封裝 EXE 做 Player 啟動與 WebView 載入、同 URL reload、hide/show、延遲開窗取消檢查；多螢幕再做關屏／開屏測試。
  5. 完成後將安裝檔另外留存為有版本名稱的發行檔，保存雜湊、測試紀錄與變更摘要。單看檔名不足以認定內容版本。
Get-Item -LiteralPath '.\build\ScreenSplitter_Setup.exe' |
  Select-Object -ExpandProperty VersionInfo
Get-FileHash -LiteralPath '.\build\ScreenSplitter_Setup.exe' -Algorithm SHA256

4.3.7 的歷史交付曾有回歸測試、實際 Qt 與 WebView smoke 證據；這些不能自動代替 4.3.8 的新建置結果。本版最終驗證以當次交付紀錄為準。

18. 交接與驗收清單

將下面資料填在團隊既有交接紀錄，不需要把帳密寫進手冊。接手人至少能自行啟停、辨識資料位置、還原設定及取得一次有效故障證據。

  • 版本：安裝檔版本、SHA-256、實際安裝日期、套用的臨時修補及可回退版本。
  • 電腦：主機名稱／IP、Windows 執行帳號、安裝路徑、實際 DATA_DIR、WebServer 連接方式。
  • Profile：default、screen2 及其他名稱；用途、設定路徑、誰負責修改，避免多人同時覆寫。
  • 兩台螢幕：設備名稱／device ID、對應 Profile、解析度、DPI、桌面排列與接線；不能只寫「大台／小台」。
  • 外部內容：網站 URL 與負責人、所需網路／帳號權限、合法登入移交管道；影片、EXE、音檔與 RDP 的位置及負責人。
  • 播放設定：每頁名稱、秒數、0 秒固定用途；特別啟用獨立 WebView 或強制更新的原因。
  • 自動行為：Windows Startup、BAT、Web 自啟、每 Profile 重啟間隔；default 的鬧鐘時間與音訊輸出。
  • 備份：最近備份日期、存放位置、包含哪些 Profile／媒體／網站資料，以及一次還原核對結果。
  • 正常播放驗收：兩個 Player 各在正確螢幕；整輪場景依序顯示，秒數正確，固定頁、暫停／繼續、上一／下一／跳轉都符合預期。
  • 內容驗收：網頁資料時間、圖磚與標記、登入狀態、影片裁切與聲音預期、EXE/RDP 的視窗與操作均由現場確認。
  • 作用域驗收：關閉／啟動單一 Profile 不影響另一台；鬧鐘僅由 default；關閉管理介面不停止播放。
  • 螢幕恢復驗收：關閉目標電視後另一畫面不被覆蓋，重新開啟後回到指定位置；以實際硬體及 LOG 的 Wait/Return 共同核對。
  • 重啟驗收：排程重啟與 Windows 登入啟動符合設定，不出現舊網路路徑／Qt DLL 錯誤，也沒有重複內容視窗。
  • 說明入口：WebAdmin「使用說明」、桌面 Admin「使用說明」／F1，以及離線 docs/usage.html 均能閱讀；閱讀不改變播放或設定。
  • 未解事項：列出未重現、待網站負責人、待硬體測試或尚未部署的項目；不要用歷史 healthy/成功畫面代替當前驗收。
